## 一、作品概述

### 1. 背景与问题

保研、考研和申请阶段，学生要在有限时间里判断“这位老师做什么、是不是我要的方向、信息是否可靠”。真实做法通常是：打开学院师资页、翻导师个人主页、在学术数据库里搜同名作者、再想办法找在读学生打听。这一过程有三个具体困难。

**第一，同名无法核对。** 中文拼音重名极严重，“刘明”“王磊”“Xiao Wang”这类姓名在学术数据库里会返回大量无关作者。学生一旦把同名者的论文当成目标导师的成果，对这个课题组的判断从第一步就错了。学院官网通常没有英文名和作者标识，学生缺乏核对手段。

**第二，信息散落在几十个页面里。** 一位导师的身份信息在学院名录页，成果在论文数据库，招生态度在个人主页或课题组页面，师生关系往往只在学位论文致谢或答辩公告里出现。这些页面分属不同站点、格式各异，学生要手工开十几个标签页，最后靠自己的记事本拼起来——拼的过程中极易把来源搞混。

**第三，公开页面不等于事实。** 学院名录没有招生年份，可能三年前的；个人主页写着“在招”可能早已招满；论文按姓名检索出来的结果可能属于同名的另一个人；共同署名不等于师生关系。网上现成的“导师评价”又多为主观打分与匿名吐槽，无法追溯，也不适合作为决策依据。

本作品聚焦一个可在参赛周期内完整验证的具体问题：**如何把散落在公开网页上的导师信息，整理成一条条带来源、可核对、可追溯的调查记录，同时明确区分“已核实”与“未知”，不替用户下结论。**

### 2. 目标、参赛方向与作品形态

**目标**：为工科学生提供一个在本机运行的导师调查工作台。用户以“选择”而非“搜索”为主要操作路径——先按姓名核对同名者身份，或依次选择一级学科、高校、研究方向定位导师；选定后在同一份档案里查看公开来源、论文线索、学术关系分析与「读研体验参考分」，逐项登记人工核查状态，最后导出 Markdown 调查记录。

**参赛方向**：申报“（一）开源赋能的 AI 应用创新”，并融合“（三）开源项目改进与生态贡献”——本作品在既有开源导师数据库项目基础上做了实质性重构与增强。

**作品形态**：本地运行的网页应用（浏览器 + 本机 Python 服务），非小程序、非云端 SaaS。选择本地形态是刻意的：导师调查涉及学生的个人判断与意向记录，这些数据不应上传到第三方服务器。工作台只监听 `127.0.0.1`，没有账号系统，用户的项目与调查记录保存在本机 `.workbench-data/` 目录。

### 3. 核心亮点

与单纯的数据收纳项目相比，本作品的差异在于**不只列名单，还分析关系并给出学生可用的参考分**。

**亮点一：关系分析按证据强度分四级，共同署名不推定为师承。** 系统把导师之间的关系分成 L1 明确师承（本人页面自述、学位论文或指导记录等公开表述，全库 **27 条**）、L2 共同指导·长期合作、L3 同门、L4 共同署名四层，每层单独标注“是否可视为师承”。**只有 L1 是师承，L4 仅为原始证据。** 这一分层使学生在查找学术出身与同门资源时，能分清哪一条是有依据的结论、哪一条只是线索。

**亮点二：学生向「读研体验参考分」，只用公开可核验信号。** 四个维度——指导结构（学生一作占比，30%）、团队承载力（组内学生数下限，25%）、组内活跃度（近三年产出，25%）、信息公开度（20%）。每一项显示依据文本、样本量与权重，可逐项核对；无公开证据的维度记为「无公开证据」并按剩余权重归一，**不视为低分**；分数旁标注“依据覆盖”比例。**论文数量、期刊档次、引用影响力与头衔一律不进入分数**——它们是学者产出，不是学生体验。

**亮点三：以“证据边界”为设计核心，而不是以“自动下结论”为目标。** 系统内所有内容都区分三种状态——有公开来源支持的事实、来自第三方转载的线索、以及“未知”。师承关系除非有明确公开表述，否则保留空白，绝不从共同署名推断。这一取舍牺牲了“看起来信息更全”的观感，换来的是每一条信息都能追溯到具体来源。

**亮点四：用开源中文向量模型解决“兴趣描述与学科术语不匹配”的检索难点。** 学生描述研究兴趣时用的往往不是学科术语。实测中，查询“我想做中文问答和知识组织”能正确召回研究方向为“自然语言处理”的导师，而按双字重合度的关键词基线做不到——这是开源嵌入模型在本场景中不可替代的作用。

**亮点五：把“人工核查”做成产品机制而非免责声明。** 每条来源默认状态为“待人工核查”，用户可逐项标记；系统根据八项核查状态生成后续待办清单，但**新增来源不会自动把核查标记为已完成**。参考分也不改变任何人工核查状态。调查记录可导出为 Markdown，包含来源类别与身份核对链接，便于学生交给老师或同学复核。

**亮点六：完整开源且可复现。** 代码以 MIT 许可开放；数据整理脚本不含硬编码路径，可克隆到任意目录运行；自带 535 项 Python 测试与 11 项前端异步测试，全部通过。

## 二、需求分析与总体方案

### 1. 需求分析

**现有做法与痛点。** 我们梳理了学生选导师时实际使用的四类信息渠道，并对照本作品的取舍：

| 现有做法 | 主要痛点 | 本作品的处理 |
|:--|:--|:--|
| 学院官网师资页 | 只有姓名职称方向，无成果、无招生信息 | 作为身份与任职的**一手来源**保存并标注采集日期 |
| 学术数据库按姓名检索 | 同名污染，“刘明”返回大量无关作者 | 提供 OpenAlex 作者候选，**必须由用户手动选择**，不自动绑定 |
| 导师个人/课题组主页 | 格式各异，招生表述时效不明 | 提取公开表述原文并保留链接；未注明年份的表述明确提示 |
| 网络上的导师评价 | 主观、匿名、无法追溯 | **不收录、不生成任何导师评价或质量打分** |

**需求优先级。** 按“做错了会不会导致判断错误”排序，我们确定了三条优先级：① 来源必须可追溯（最高，做错则全盘失效）；② 同名必须可核对（做错则论文归属错人）；③ 未知必须显示为未知（做错则学生误以为信息完整）。功能丰富度排在三条之后。

**需求来源说明。** 本作品的需求判断来自团队自身在保研/考研信息搜集中的实际经历，以及对公开渠道信息形态的分析。**我们尚未开展独立的用户调研或访谈**，因此本报告不对“提高效率”“改善决策”作任何量化声称——这一点在第五章“验证结果”中如实说明。

### 2. 总体方案

系统采用“本地服务 + 浏览器界面 + 本机数据”的三层结构，全部在本机运行。

```
┌─────────────────────────────────────────────────────────────┐
│  浏览器界面（workbench/web/）                                 │
│  index.html 主页       desk.html 调查工作台                    │
│  assets/*.js  异步请求、竞态防护、手动添加导师/论文             │
└───────────────────────────┬─────────────────────────────────┘
                            │ 本机 HTTP（127.0.0.1:8765）
┌───────────────────────────┴─────────────────────────────────┐
│  本机服务（workbench/app.py, FastAPI + Uvicorn）              │
│                                                              │
│  目录与档案          检索              调查与证据              │
│  catalog.py          search.py         investigation.py       │
│  · 学科→高校→方向     · 语义检索        · 身份/论文/关系整理    │
│  · 同名分别保留       · 关键词基线      · DOI 元数据核对        │
│  · 八项核查状态       · 向量缓存        · 待办清单生成          │
│                                                              │
│  core.py 本机存储   openalex.py 作者候选   public_research.py  │
│  · 项目/调查 JSON   · 只返回候选，不绑定   · 公开页面提取        │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────┴─────────────────────────────────┐
│  数据层                                                       │
│  已入库成果：data/processed/、workbench/reference/            │
│  用户数据：.workbench-data/（项目、调查、页面缓存、向量索引）    │
│  外部接口（可选、需联网）：OpenAlex、Crossref                  │
│  本地模型：.workbench-data/models/（bge-small-zh ONNX）        │
└─────────────────────────────────────────────────────────────┘
```

**输入输出。** 输入为：① 已入库的公开师资名录与成果记录；② 用户导入的 CSV/JSON 资料；③ 用户手工添加的导师与论文；④ 可选的 OpenAlex/Crossref 联网查询。输出为：① 浏览器中的导师档案；② 逐人 Markdown 调查记录；③ 项目 JSON 导出。

**主要运行流程。** 用户进入主页 → 选择路径（按姓名 / 按学科）→ 系统列出候选并**分别保留同名者** → 用户选定身份 → 系统展示该身份已保存的公开来源、论文与论著、师承表述、招生记录 → 用户逐项核查并登记状态 → 导出 Markdown。

### 3. 可行性与成本

**算力**：不需要 GPU。语义检索用的 ONNX 模型约 95 MB，在普通笔记本 CPU 上完成 10 条资料的向量计算约 4 秒，之后命中本地向量缓存则低于 0.1 秒。

**软件**：全部为开源组件（详见第三章与附录）。Python 3.10–3.12、Node.js 18+（仅测试用）。

**数据**：来源于高校/科研机构官网公开师资页、学校研究生招生目录公开 PDF、以及 Crossref 公开元数据接口。**不采集登录墙、付费墙或私人渠道内容。**

**设备与时间**：单台笔记本即可完成开发与演示。从既有开源导师数据库出发，经过史料整理、目录重构、检索实现、前端竞态修复、测试补齐等阶段迭代而成。

**成本结论**：无付费 API、无云服务器、无专用硬件。唯一外部依赖是可选联网查询（OpenAlex / Crossref 匿名配额），离线状态下除该功能外全部可用。

## 三、AI 技术与开源及第三方资源选择

### 1. AI 技术作用

本作品的 AI 作用在**两处**，且都不是"给导师打分"：

- **语义检索**：把用户用自然语言描述的研究兴趣，与各学科导师的研究方向文本匹配起来。
- **数据治理**：用同一个开放嵌入模型辅助两件人工做不完的事——**方向补全**（把已抓到的
  履历文本映射到方向标签）与**同名消歧**（判断同名两条记录是不是同一个人）。

第二处是本作品与"接一个大模型做问答"最不一样的取舍：**把 AI 用在数据质量上，而不是用在
对人的评价上。** 两处都做了离线评测，并且都**照实报告了不利结果**（见第五章）。

**为什么需要 AI。** 本作品默认覆盖 38 个工学一级学科（2022 年目录 08 门类）的导航数据，导师的研究方向文本差异极大。如果只做关键词匹配，“我想做中文问答和知识组织”与“自然语言处理”之间没有共同的双字片段，关键词基线直接漏召回。语义嵌入把两者映射到同一向量空间，用余弦相似度完成匹配。

**如何验证 AI 输出。** 我们做了两件具体的事：

1. **并列关键词基线。** 系统同时提供“关键词基线”（按查询与文本的双字重合度排序）与“语义检索”，让用户自己核查 AI 是否真的有帮助，而不是只给一个黑盒结果。两个模式的分数与排序都在界面上可见。
2. **预置查询集评估。** 在 8 条公开来源试点资料上，事先写定 8 个查询与期望命中项，脚本化比较两种模式的 Top-1 / Top-3（结果见第五章）。

### 1.1 方向补全：混合策略，并报告了嵌入模型输给关键词的结果

**问题。** 全库有 **4,030 条**记录的研究方向仍是「方向待补」，但其中 **4,007 条已经读到
个人主页的履历文本**（中位长度 424 字）、1,595 条还有论文目录。**缺的不是数据，是把已有
文本映射到方向标签这一步。**

**做法。** 用 `BAAI/bge-small-zh-v1.5` 把 256 个方向标签与履历文本各自编码，取余弦相似度。
词表从 2,397 种已有方向取值中过滤（要求出现 ≥5 次），并**剔除「不分研究方向」这类退化标签**
——否则模型只要全猜这一类就能把准确率刷上去。

**评测（400 条留出验证，随机种子 42）。** 把已有方向的记录的方向藏起来，只用履历等文本预测：

| 方法 | Top-1 | Top-3 |
|:--|--:|--:|
| 关键词基线 | 64.0% | 70.2% |
| 嵌入模型（bge-small-zh-v1.5） | **9.0%** | 53.2% |
| **混合（关键词优先，弱则回落嵌入）** | **66.2%** | **74.5%** |

**必须如实说明：嵌入模型单用时 Top-1 只有 9.0%，远低于关键词基线。** 按「真值标签是否被
字面写进文本」分层后原因清楚：

| 分层 | 占比 | 关键词 Top-1 | 嵌入 Top-1 |
|:--|--:|--:|--:|
| 履历里直接写了方向 | 63% | **95.6%** | 4.4% |
| 需要语义推断 | 37% | 10.7% | **16.8%** |

高校个人主页常直接写「研究方向：XXX」，这类记录关键词就能命中；嵌入模型把整段履历
（职称、任职时间、行政职务）一起编码，方向信号被稀释。**但在没有字面线索的那 37% 上，
嵌入确实强于关键词**——这是 AI 的真实价值区间，也是我们采用混合策略、而不是宣称
"用了 AI 所以更强"的原因。

**保守性。** 相似度低于 0.55 的 **455 条一律留空**；推断结果只作为**建议**落在
`.workbench-data/direction-inference/suggestions.json`，逐条带分数与方法标记，
**不覆盖原始 `direction` 字段**，供人工复核。

### 1.2 同名消歧：用个人主页 URL 当真值

**问题。** 全库有 **908 组同名**（占不同姓名的 7.0%，涉及 2,231 条记录），其中 **224 组是
同校内同名**——最容易把两个人看成一个人。既有实现只用"学校 + 院系"硬约束，宁可判
"同名待核"也不猜，但它没有利用履历文本这条强信号。

**真值从哪来。** **个人主页 URL 本身就是可核验的真值**：同一 URL 必然是同一人，两个不同
URL 必然是不同人。`homepage` **只用作标签，绝不进入特征**。按此构造 **535 对**带真值样本
（同人 80 / 异人 455）；**542 个同名组因缺主页被整组跳过**，不补标签、不猜。

**结果。**

| 特征 | AUC |
|:--|--:|
| 仅机构是否相同 | 0.952 |
| 仅履历文本嵌入相似度 | 0.849 |

| 方法 | 精确率 | 召回率 | F1 |
|:--|--:|--:|--:|
| 朴素基线（机构相同即判同人） | 64.5% | 100% | 78.4% |
| **机构相同 + 嵌入相似度 ≥0.7** | **86.7%** | **90.0%** | **88.3%** |

在机构相同的前提下加一道嵌入阈值，**精确率从 64.5% 提升到 86.7%**，召回只降 10 个百分点。
它挡掉的正是"同校、同名、但不是同一个人"这类最容易看错的错误。

**一个必须写明的失败模式。** 嵌入相似度高**不能**覆盖"主页不同"这个硬事实：待核清单首位的
「某校 王晶 · 相似度 0.990」看起来像同一个人，但采集该校名录时已确认这两个主页地址
**分别指向两个不同的个人页**——是两个人。原因是同院系履历高度模板化（"2014- 某校 副教授"
这类句式），嵌入会把两段模板相似的履历判得很近。因此本模块定死优先级：
**主页判等 > 嵌入相似度**，嵌入只用于排序与提示，**系统不自动合并任何记录**。

这也解释了为什么"仅机构"的 AUC（0.952）反而高于"仅嵌入"（0.849）——机构是硬信号，
文本相似度会被模板稀释。**AI 在这里是提高精确率的辅助，不是裁判。**

### 1.3 界面上能看到这些 AI 结果

两处 AI 产物接进了导师详情页，作为一个独立区块「**AI 建议（待复核）**」：方向建议（含相似度、
所用方法、次选方向）与同名待核（含另一方院系与主页链接）。区块内常驻一句说明：
**"AI 推断结果，仅供人工复核时参考，不构成事实、不改变参考分、也不会被自动写入数据。"**
产物缺失时区块静默隐藏，不影响其它功能。

**明确不做的 AI 用途。** 我们不使用 AI 对导师作评价、打分、排序或推荐，也不让 AI 自动判定论文归属或师生关系。这些判断一旦由模型自动完成，错误的代价由学生承担，且无法追溯。系统对相似度分数的定位是“找资料的线索”，界面上明确写出它不是可信度、适配度或优劣分。

### 4. 融合方式

本作品的“AI + 开源”不是“调用一个模型接口”就结束，而是形成了一条完整链路：

**开源模型提供语义能力 → 本作品把它接入“证据可追溯”的数据结构 → 检索结果直接带着来源回到档案里。**

具体而言：向量检索只在**用户已选定的资料集**内排序（`search.py` 中的 `search()` 先按学科/高校过滤再算相似度），因此检索结果天然带着结构化学科与单位标签；每条结果同时返回 `evidence_count`（该导师已有多少条来源），用户能立刻看出“这条命中是否已有来源支撑”。**这是与通用 AI 应用最实质的区别**：通用做法把模型输出当作答案，本作品把模型输出当作“去找哪份档案”的线索，答案仍要回到公开来源上核对。

相较既有同类作品，本作品的实质改进有三点：① 从“按姓名检索并自动绑定作者”改为“列出同名候选、由用户核对身份”；② 从“只列名单的数据收纳”改为“关系分析 + 学生向参考分”，且两者都只用公开可核验信号、每项可点开看依据；③ 从“单一学科数据库”扩展为覆盖 38 个工学一级学科的导航框架（2022 年目录 08 门类；另有 79 个非工科学科数据保留在库中并可切换显示，不作删除）。

**同名处理的关键流程**：同名者作为独立条目保留，不合并。导入去重只在姓名、机构、院系、主页四项**全部相同**时才判为重复——宁可留两条让用户判断，也不冒把两位同名教师合并的风险。

### 2. 关键实现

**（1）向量缓存与指纹校验。** 资料向量按项目缓存于 `.workbench-data/indexes/<project_id>.npz`。缓存文件内同时保存资料指纹（资料 ID 与文本的 SHA-256）和模型名；读取时两者都匹配才复用，否则重新计算。这样既避免了每次检索重复推理，又保证资料修改后不会用到过期向量。

**（2）前端异步竞态防护。** 用户在快速切换学科、高校、方向、导师时，先发出的请求可能后返回，从而覆盖当前选择——这是同类工具常见且难察觉的缺陷。实现上为每类请求保留版本序号，回包时只有序号仍为最新才允许渲染。该行为由 11 项前端测试专门覆盖（如“旧学科响应不能覆盖较新的选择”“切到新导师后旧资料请求不得刷新新档案”）。

**（3）来源状态与“不自动完成核查”。** 每条来源携带 `status` 字段，默认“待人工核查”。整理任务（身份来源、论文候选、关系证据、既有档案四项离线运行）完成后**不会**修改任何来源的状态。这一约束写在模块文档字符串里并有测试保护，防止后续迭代为了“体验流畅”而让系统自动认证来源。

**（4）公开页面提取的约束。** `public_research.py` 只读取已在代码中登记的院系名录与个人主页；手动录入的任意网址**不进入自动抓取**，避免把工具变成任意 URL 抓取器。页面读取失败时不清空既有成功结果与用户笔记。只保存提取出的简短事实与书目，不重新发布网页全文。

**（5）测试策略。** 535 项 Python 测试覆盖个人页解析、身份来源约束、年度招生记录匹配、失败更新保留资料、重复导入去重等；11 项前端测试用 Node 内置测试器在无浏览器环境下验证异步竞态。测试不替代浏览器交互验收，这一点在文档中明确写出。

这是为了根治一类历史问题：报告曾长期写着"10,441 条"，而实际早已过万。

**（6）机构分布达标：一个我们自己定出来、并且卡住了自己的标准。**

一个学科"有人"不等于"能用来做跨校比较"。如果某学科 90% 的记录来自同一所学校，学生在上面
看到的"不同学校导师"其实是同校几位老师，跨校比较就是假的。因此本项目定了一条硬标准：

> **最大单一机构占比必须 < 60%**，该学科才可用于跨校比较；未达标的在界面上按实际数字展示，
> 不宣称已覆盖。

这条标准的执行工具是 `python -m workbench.tools.distribution_audit`，它同时给出**还差多少人**：

```
补入后最大机构占比 = max(原主导数, 补入数) / (原总数 + 补入数)
```

**这条式子在实践中救回了一个错。** 0801 力学原有 35 条、上海交通大学 34 条（97.1%）。
我们补入北京大学 96 位后，主导校从上海交大换成了北京大学（96/131 = **73.3%**）——**只是把
偏斜挪了个位置，仍未达标**。第二步按式子算出"需再补 ≥29 位且必须来自第三所学校"，
补入同济大学 73 位后变为 96/204 = **47.1%**，才真正达标。

**这条标准也让我们主动放弃了若干"能取但不能用"的来源**（宁可数字小，不要假分布）：

| 被放弃的候选 | 能取到 | 为什么不用 |
|:--|:--|:--|
| 大连理工「力学与航空航天学院」 | 184 条 | 学院把 0801 力学与 0825 航空宇航合设，整体归入属弱归属 |
| 南京航空航天大学 航空学院、浙江大学 航空航天学院、北京理工大学 空天科学与技术学院 | 各数十条 | 均设力学系，同属航空＋力学合设 |
| 武汉大学 计算机学院 | 106 条 | 横跨 0812 与 0835，整院归入 0835 属弱归属 |
| 西安交通大学 核科学与技术学院 | 67 条 | 补入后该校占 63.8%，仍违反 < 60%，取了也没用 |
| 重庆大学 建筑城规学院 | 65 条 | 建筑＋城乡规划＋风景园林合设，页面只到学院一级 |
| 哈尔滨工程大学 核学院（整页） | 120 条 | 全收会让该校占 76.4%，把"独大"从上海交平移过去 |

**同一条标准还决定了"只取一部分"的取舍**：哈工程整页 120 人只取学院仅有的两个"系"25 人；
同济交通运输学院 197 人只取交通信息与控制系 35 人；华南理工食品学院只取"教授"序列 48 人。
每个模块的 docstring 与每条记录的备注都写明了覆盖范围——**"取了多少"必须能被读者看出来，
否则 25 人看起来就像全系只有这些人。**

**当前状态**：38 个工学学科中 **29 个达标、9 个未达标**（未达标的多为设置高校本身很少的
学科，如兵器 1 所、纺织 1 所、林业 1 所，已确认公开入口不可达）。这个比例随收录进展变化，
以 `distribution_audit` 的实时输出为准。

**（7）尚未达到的目标（如实说明）。**

- **没有独立用户研究。** 未开展访谈、问卷或任务实验，因此本报告不声称“提高效率”或“改善决策”。检索评估是 8 条资料上的工程冒烟检查，样本量小，不能证明语义检索优于关键词。
- **全国覆盖率未评估。** 117 个学科“均有名单”不等于全国完整。部分学科的收录人数仍很少（最少的 0839 网络空间安全 34 位、0827 核科学与技术 38 位，另有多达 18 个学科的“最大单一机构占比”超过 60%，尚不足以做跨校比较，逐项清单见 python -m workbench.tools.distribution_audit），且部分线索来自第三方转载名录，已在页面与文档中分开标明来源强度。
- **数据完整度有限。** 公开来源已覆盖相当规模的条目，但每个导师的论文、师承、招生信息远未补齐；没有公开依据的师承保持空白。
- **模型对英文与专业术语的表现未系统验证。** 所用中文嵌入模型在英语查询和生僻专业术语上的效果尚未评估。
- **署名结构推断的已知误差。** 历史专题中的团队规模、署名健康度等为文献计量推断值，存在同名与漏检误差，工作台中仅作为线索展示，不作为结论。

## 六、创新性与开放价值

### 1. 创新性

与既有方案比较，本作品的实质改进集中在三点：

**① 交互范式：从“检索”改为“核对”。** 同类工具默认“输入姓名 → 返回结果”，把同名消歧问题留给了用户却又不提示。本作品把同名候选**显式并列展示**（含学校、院系、一级学科、方向、来源数量），要求用户先核对身份再调查，并在论文线索环节坚持“只给候选、由用户选择”，不自动绑定作者。

**② 产品伦理：从“生成评价”改为“呈现证据边界”。** 本作品明确不生成导师评价、不打分、不排名，也不让 AI 自动判定师生关系。取而代之的是八项人工核查状态与“不自动完成核查”的机制约束。这是一个操作性取舍：它让产品在演示时“看起来信息更少”，但让每一条信息都可追溯。

**③ 检索设计：并列基线与多学科导航框架。** 语义检索与关键词基线并列展示，便于用户与评审共同核查 AI 是否真有帮助；覆盖 38 个工学一级学科的导航框架使工具不局限于单一专业；另有 79 个非工科学科的数据保留在库中并可切换显示。

**与上游开源项目的关系（开源项目改进与生态贡献）：** 本作品在既有开源导师数据库项目基础上做了实质性重构——新增工学范围导航与选择式定位、同名核对机制、调查档案与本机存储、检索评估脚本、76 项 Python 与 11 项前端测试、以及逐批可追溯的核对记录。上游项目的原始数据与许可声明保持不变。

## 七、合规、安全与风险说明

### 1. 开源及第三方许可合规

所用资源均为 MIT / Apache-2.0 / BSD-3-Clause 等宽松许可，与本项目以 MIT 开放代码的目标兼容。完整清单、版本、来源、关键义务与合规状态见附录一。要点：

- **署名义务**：MIT 与 BSD 许可要求保留版权声明与许可声明。本作品在仓库根目录保留 `LICENSE`（MIT），引用第三方组件时在《开源及第三方资源使用清单》中列明名称、版本与许可，未删除或修改第三方源码中的许可头。
- **再分发**：本项目不打包再分发第三方组件的二进制文件。用户通过 `pip install -r workbench/requirements.txt` 自行安装，各组件由原始渠道分发。
- **模型文件**：中文嵌入模型（约 95 MB）**不进入仓库**，由 FastEmbed 在首次使用时从模型托管站下载到本机被 Git 忽略的目录，因此不涉及模型权重的再分发。
- **对应源代码提供**：本项目未修改任何第三方库源码，不触发 copyleft 类条款。
- **数据许可**：Crossref 元数据为公开接口数据；OpenAlex 数据以 CC0 提供；第三方教师网页原文权利归原权利人，本项目只保存少量事实与链接，不重新发布全文。
- **“公开可访问”≠有再分发授权**：本项目对此的处置是——只保存事实性信息与来源链接，原始页面缓存保留在本机且不进入公开仓库。

### 2. 数据、权利与隐私

**数据来源与获取方式**：高校/科研机构官网公开师资名录页与个人主页、学校研究生招生目录公开 PDF、Crossref 公开接口、OpenAlex 公开接口、公开的学位论文与答辩公告。

**权利状态与使用边界**：入库内容为**事实性信息**（姓名、任职单位、院系、研究方向、公开来源链接、公开招生表述、论文元数据）。第三方网页原文不复制、不重新发布。

**脱敏与个人信息保护**：

- **不收录、不存储、不展示任何邮箱地址**。名录层、产物层与兜底清洗三层防护，并有 CI 校验（未通过则构建失败）；
- 不采集电话、房间号、出生日期、性别、籍贯等个人信息；
- 从历史调查档案提取内容时，逐行过滤含邮箱、电话、房间、出生、性别、籍贯、`@` 的行；
- 用户自己的项目与调查记录保存在**本机**，不上传任何服务器；服务只监听 `127.0.0.1`，无账号系统，文档明确提示不要直接暴露到公网；
- OpenAlex 的 API key（可选）只在本机进程环境变量中读取，不写入项目文件。

**更正与删除机制**：任何人对自己的信息可提出更正或整条移除请求，**无需提供任何证件**，承诺 7 个工作日内处理。

### 3. AI 输出、知识产权与内容安全

**模型幻觉风险与处置。** 本作品的 AI 用途限于向量检索，**不生成任何事实性文本**，因此不存在“模型编造导师信息”的路径。检索结果的排序错误（如把不相关导师排进前三）已在第五章实测并如实披露。

**相似度分数的误用风险与提示。** 风险在于用户把相似度当成导师优劣。处置：① 界面与文档明确写出“相似度只用于找资料，不评价导师水平或指导质量”“语义分数没有跨查询可比性”；② 不提供任何基于相似度的导师排名；③ 读研体验参考分与语义相似度相互独立，且明确不进入论文数量、期刊档次、引用与头衔。

**提示注入风险。** 作品不把抓取的网页文本交给任何大模型处理，也不据此执行动作，因此不构成提示注入的攻击面。公开页面提取仅做结构化字段解析。

**数据错误风险。** 主要风险是信息过时或同名误配。处置：① 每条内容带来源链接与来源类别，招生记录带年份；② 学院名录类“无年份”来源明确标注为身份与任职记录，不当作年度招生；③ 军兵种作战学等少数条目依据为第三方转载，页面与文档中单独标明“来源强度”；④ 未检索到资料时显示“未知”，不填充推断内容。

**AI 生成内容的权利核查。** 开发中使用了生成式 AI 辅助（见第四章第 3 节）。团队对纳入作品的内容做了人工审阅与实际运行验证、来源与权利核查，确认未引入权利状态不清的代码；报告全部统计数字可由仓库脚本复现。

**内容安全。** 作品不含违法违规、不良导向或恶意代码内容。已移除纯负面招生表述清单，避免对个人形成负面指向；检索与展示中不含对个人的评价性用语（由公开前审计脚本自动检查）。

### 4. 知识产权与公开边界

- **团队自主创作部分**（`workbench/` 与 `tools/` 代码、文档、整理后的数据）权利归团队成员；
- **第三方部分**：开源软件与模型的著作权归各自作者；第三方教师网页内容归原权利人；本项目不改动第三方权利归属；
- **无共同权利人或单位授权边界问题**：本项目未使用学校、实验室、实习单位或项目承担单位的资料，不涉及职务成果或商业秘密，亦未申请专利；
- **公开范围**：仓库公开代码与整理后的结构化事实数据；不公开原始网页缓存、模型权重文件、本机用户数据（项目与调查记录）。

### 5. 其他风险与适用边界

| 风险 | 说明 | 当前处置 |
|:--|:--|:--|
| 招生信息时效性 | 公开表述可能滞后 | 标明年份与来源；提示以导师回复与院系最新通知为准 |
| T3/T4 类“公开证据较少”被误读 | 可能源于同名、英文署名不一致、中文文献未覆盖等数据原因 | 文档明确写出“不代表水平或指导质量” |

## 八、总结与展望

### 1. 项目总结

**完成情况。** 本作品完成了一个可运行的本地导师调查工作台：覆盖 38 个工学一级学科的选择式导航与同名核对，以及关系分析四级分层与学生向读研体验参考分、带来源与状态的调查档案、八项人工核查与待办生成、OpenAlex 作者候选与 Crossref DOI 核对、CSV/JSON 导入、Markdown 导出；配套 76 项 Python 测试与 11 项前端测试全部通过，公开前审计 16 项通过、0 项阻塞。

**主要价值。** 把“导师信息搜集”从打开十几个标签页、靠自己拼记事本，变成一份份带来源、可核对、可导出的调查记录；并用产品机制保证系统不会替用户对导师下结论。

**团队收获。** 一是理解了“证据边界”比“功能丰富”更难也更重要——把“未知”如实显示出来，需要抵抗住把页面填满的冲动；二是经历了一次典型的静默失效排查：采集脚本字段名写错导致机构校验匹配一切、81.7% 匹配失真，最终靠独立于采集过程的产出侧复核抓出来，此后把“不要只信任采集过程，要独立复核最终数据”写进了维护指南；三是实践了在真实项目里判断“什么该交给 AI、什么绝不能交给 AI”。

**未完成事项。** ① 无独立用户研究与任务实验，效率与决策改善效果未知；② 全国覆盖率未评估，部分学科收录很少；③ 多数导师的论文、师承、招生信息尚未补齐；④ 尚未向上游提交 Issue/PR；⑤ 语义检索的弱尾噪声未做阈值过滤，目前靠并列关键词基线缓解。

### 2. 后续计划

1. **功能优化**：为语义检索增加相似度阈值与关键词二次过滤，降低弱尾噪声；继续修复公开页面解析的漏读问题。
2. **测试扩展**：扩大独立标注的检索评估样本（跨学校、跨学科、多人独立标注），使“AI 是否真有帮助”有可复现的量化依据；补充同名消歧的专项评测集。
3. **数据补充**：优先补录人数最少的学科；对每批新增数据保留逐人来源核对记录。
4. **开放维护**：按许可证与维护计划持续更新；每次推送前运行公开前审计与全新克隆自检；通过 Issue 模板接收更正与建议。
5. **社区协作**：把可复用的方法（来源校验、站点模板误判过滤、并列基线的检索评估）整理为独立文档，并向上游开源项目提交改进建议。
